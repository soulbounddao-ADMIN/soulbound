# Task 3 Reimplementation Decision

## Status

The prior Task 3 builder output is rejected and discarded.

Task 3 will be reimplemented from a clean post-Task-2 state by Codex as a one-time exception to the normal builder workflow.

Codex must not self-approve. Final review remains separated and will be performed by Claude Code / Cowork as a read-only semantic audit.

## Scope of This Decision

This decision applies only to Task 3.

Task 3 is the database/security boundary for SoulBound Phase 1 v1.3. It includes:

- Supabase schema
- Row-Level Security
- RPC functions
- idempotency behavior
- storage bucket policy
- Persona Clip retention behavior
- local seed data

Because Task 3 controls authorization, auditability, state transitions, and sensitive media retention, it requires stricter implementation discipline than scaffold/UI work.

## Evidence

The detailed failure evidence is recorded in `docs/TASK3_AUDIT_FINDINGS.md`.

That audit found that the prior Task 3 output passed some mechanical gates, but failed semantic and process checks. The most important findings were:

1. Task 3 scope drift: `docs/TASK3_BUILDER_PROMPT.md` was modified/corrupted even though Task 3 was DB/config only.
2. RPC/schema mismatch: RPC functions inserted `idempotency_key` into `audit_logs`, but the schema did not define that column.
3. Frozen contract violation: RPC functions used reason codes outside the frozen `AdmissionReasonCode` contract, including `application_submitted` and `review_started`.
4. RLS column exposure: applicant row-level select exposed the full `admission_applications` row, including `review_summary`.
5. RLS update overbreadth: "limited update" policies did not actually prevent clients from mutating restricted columns such as `role`, `membership_status`, `status`, `reviewer_id`, `reviewed_at`, or `review_summary`.
6. Audit integrity issue: `approve_application_tx` recorded an incorrect `from_status` because the application row was updated before the previous status was captured.

## Decision

The prior Task 3 output will not be patched in place.

The working tree will be reset to a clean post-Task-2 state for Task 3 scope.

Task 3 will be reimplemented from scratch by Codex.

The fix-round builder prompt embedded in `docs/TASK3_AUDIT_FINDINGS.md` is superseded by this decision. It remains as historical evidence of the failed round and its required fixes, not as an instruction to continue with GLM / Claude Code as the builder for Task 3.

## Exception Workflow

Normal workflow:

- Builder: GLM / Claude Code
- Audit: Codex + Cowork

Task 3 exception workflow:

- Builder: Codex
- Final reviewer: Claude Code / Cowork
- Codex self-approval: prohibited

## Rationale for Codex Builder Exception

Task 3 is not simple scaffolding.

Task 3 contains security-critical database logic, including RLS, RPC transition guards, idempotency semantics, storage policies, and Persona Clip retention.

For this task, implementation quality depends on precise alignment between the frozen TypeScript contract and SQL behavior.

GLM / Claude Code may still be used later for scaffold, UI, repetitive file generation, and log collection. It should not be used as the primary builder for Task 3's database/security boundary.

## Reimplementation Requirements

Codex must account for the prior audit findings.

Specifically:

1. RLS must not be treated as column-level protection.
2. Applicant clients must not read `review_summary`.
3. Applicant clients must not update restricted application columns.
4. Users must not update `role` or `membership_status`.
5. RPC functions must not use reason codes outside the frozen `AdmissionReasonCode` contract.
6. RPC idempotency must be schema-consistent.
7. `approve_application_tx` must capture `from_status` before updating the application row.
8. Persona Clip terminal retention must be preserved.
9. No literal `commit` or `rollback` tokens may appear in `supabase/migrations`.
10. No concrete-chain references may appear in code.

## Review Requirement

After Codex completes Task 3, Claude Code / Cowork must perform a read-only audit.

The audit must verify:

- scope control
- `supabase db reset`
- RLS semantics
- RPC guards against `admission-policy.ts`
- idempotency behavior
- `review_summary` non-exposure
- restricted-column non-mutability
- Persona Clip terminal retention
- `packages/core/src` untouched
- no Task 4 implementation leakage

Task 4 must not begin until Task 3 passes this separated review.
